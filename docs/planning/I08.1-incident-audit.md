# I08.1 — Auditoría funcional transaccional

## Estado y trazabilidad

Issue [#75](https://github.com/xbasets82/Nextriva/issues/75), aprobada. HU14, limitada a registrar las operaciones ya disponibles y exponer las actividades existentes en el detalle.

## Decisiones aprobadas

- Reutilizar la entidad `incident_activities`; no crear una tabla funcional adicional.
- Cada mutación y su actividad se confirman en la misma transacción PostgreSQL. Las denegaciones y validaciones rechazadas no añaden actividades.
- Actor y fecha los establece el servidor. Las actividades no incluyen cuerpos de comentarios ni otros textos privados innecesarios.
- Los comentarios siguen siendo registros independientes en `incident_comments`. Su alta registra `COMMENT_ADDED` con `changes: { commentId }`.
- `GET /api/incidents/:id` conserva el orden ascendente por `createdAt` y, para empates, por `id`.
- La migración solo añade `COMMENT_ADDED` al enum existente. No se hace backfill ni se inventa historial previo.
- I08.1 no crea una ruta general de edición, pantalla nueva de historial, ni las acciones reservadas a I08.2.

## Operaciones conectadas

La creación, asignación/reasignación, inicio, actualización de borrador, envío, aprobación/rechazo y alta de comentario usan el mismo punto de escritura de actividad del módulo Incidents dentro de su transacción actual. La actividad de comentario referencia el comentario mediante UUID sin duplicar su texto. No hay un endpoint de edición general en el código actual, así que no se introduce uno para esta fase.

## Pruebas previstas y TDD

- Vitest unitarias existentes del módulo Incidents como regresión; no se añadió una prueba unitaria aislada para el schema declarativo. La variante `COMMENT_ADDED` se comprobó mediante el contrato/tipos OpenAPI generados y la persistencia HTTP.
- Integración HTTP con PostgreSQL temporal: actor/tipo/carga/fecha del evento, ausencia de evento en rechazo, FK, rollback al fallar la inserción y preservación de comentarios.
- Playwright Chromium con API y PostgreSQL temporal: agregar comentarios desde UI y verificar el historial recibido por detalle, su referencia a comentarios y orden estable.
- No se modifica ni limpia `nextriva_dev`; el runner crea y elimina una base temporal aislada.

## Límites

No se rellenan actividades para registros anteriores a la implementación. No se añade evento por edición general mientras esa operación no exista. La verificación de lector de pantalla y otros navegadores no aplica a una pantalla de historial nueva, porque esta fase no agrega interfaz; la prueba E2E solo comprueba el contrato que consume la vista existente.
