# I07.2 — Registro y envío de solución

## Estado y trazabilidad

**Estado:** aprobado para desarrollo; Issue #68 `status:approved`.
**HU:** HU12 — Documentar solución.
**Dependencia:** I07.1 integrada en `main` (Issue #66, cerrado; `origin/main` verificado en `93423ad803972b9ba6eaeb14d0058bfc279f96e1`).
**Alcance:** guardar/editar/borrar el borrador de solución y enviar una solución a validación. No incluye aprobar, rechazar ni cerrar la incidencia (I07.3).

## Decisiones aprobadas para el Issue

- Solo el responsable asignado puede guardar o enviar una solución.
- Guardar, modificar o vaciar un borrador solo se permite cuando la incidencia está `IN_PROGRESS` y la promoción está activa.
- Un borrador puede estar vacío; su ausencia se representa como `null`.
- El texto admite como máximo 5.000 caracteres. El envío requiere texto no vacío tras recortar espacios.
- Guardar un borrador no cambia el estado ni registra actividad de envío. Un cambio real registra `SOLUTION_UPDATED` en la actividad histórica, en la misma transacción que el texto y la versión. Una escritura sin cambio es idempotente y no modifica actividad, versión ni `updated_at`.
- Enviar requiere responsable, incidencia `IN_PROGRESS`, promoción activa y al menos un validador elegible distinto del presentador.
- El envío pasa a `PENDING_VALIDATION`; esto no aprueba ni cierra la incidencia. `solution_submitted_by_id` y `solution_submitted_at` los establece el servidor.
- Estado, versión, datos del envío y actividad correspondiente se escriben en una única transacción. Cualquier rechazo o fallo revierte todas las mutaciones.
- No se puede editar el borrador en `PENDING_VALIDATION` ni `CLOSED`.
- No se añaden entidades ni campos propios de aprobación, rechazo o cierre.

## Contratos HTTP aprobados

Contratos aprobados en el Issue #68:

- `PUT /api/incidents/:id/solution` para guardar, modificar o vaciar el borrador, con control de versión.
- `POST /api/incidents/:id/submit-solution` para enviar el borrador no vacío a validación, con control de versión.

El primer endpoint recibe `{ solution, version }`; el segundo `{ version }`. Ambos usan CSRF y devuelven 200 con la incidencia resultante. La autorización y la política de visibilidad se aplican en servidor reutilizando las políticas existentes; los tipos cliente se generan desde OpenAPI.

Una versión obsoleta responde 409 con `code: INCIDENT_VERSION_CONFLICT` también si otra petición ya envió la solución. Antes se comprueban visibilidad y autorización del responsable; un actor no autorizado conserva 403/404. Guardar sin cambios devuelve la misma forma de respuesta que guardar un cambio, sin relaciones adicionales.

## Separación de incrementos

- **I07.2:** borrador, envío, transición `IN_PROGRESS` → `PENDING_VALIDATION` y actividad atómica de envío.
- **I07.3:** aprobación/cierre y rechazo con motivo; no se implementa ni se adelanta aquí.
- El guardado del borrador no constituye un evento de envío. Los cambios efectivos se registran como `SOLUTION_UPDATED`; la repetición idempotente no genera actividad.

## Corrección vinculada — Issue #69

La revisión previa a publicar detectó que I02/I04 podían retirar al último validador después del envío y que el límite nativo UTF-16 de la UI no coincidía con los 5.000 puntos de código del servidor. Issue #69 y su implementación conjunta en esta rama fueron aprobados expresamente.

- Desactivar/degradar usuarios o retirar participantes no puede dejar incidencias pendientes sin un validador activo autorizado distinto del presentador. La comprobación y la escritura comparten transacción; el advisory lock `210021` coordina estos escritores con el envío, antes de los bloqueos de promoción/usuario/incidencia.
- Se mantiene la elegibilidad global de ADMIN y se permite el cambio si persiste otro candidato. Las denegaciones responden 409 y revierten usuario/vinculación/sesiones sin modificar incidencia ni actividad.
- UI y API cuentan puntos de código Unicode; 5.000 son válidos y 5.001 se rechazan. El formulario anuncia el error y enfoca el campo.
- Pruebas HTTP/PostgreSQL de denegaciones, casos permitidos y carreras utilizan una base adicional propia del fixture, sin alterar los actores globales de otras pruebas.
- La [evidencia específica](../tfm/evidencias/2026-10-23-issue-69-independent-validator-unicode.md) conserva RED/GREEN reales, fallos de preparación corregidos y limitaciones pendientes. No se adelanta I07.3.

## Riesgos y límites

- Las dos migraciones aditivas añaden campos de solución y eventos al esquema de `incidents`/`incident_activities`; se aplicaron desde cero con PostgreSQL temporal.
- Evitar revelar si una incidencia privada existe; mantener 404 para recurso no visible y la distinción aprobada para acciones prohibidas sobre recursos visibles.
- La actividad reutiliza `incident_activities`; se amplía el enum existente con `SOLUTION_UPDATED` y `SOLUTION_SUBMITTED`, sin crear una entidad de historial nueva.
- Las pruebas de integración y E2E deben validar host/puerto/base permitidos mediante el runner seguro y usar únicamente PostgreSQL temporal aislado.
- La evidencia TFM está en [I07.2](../tfm/evidencias/2026-10-23-i07-2-incident-solution.md); conserva la limitación real del ciclo RED del envío y documenta la prueba HTTP aislada de ausencia de validador.
