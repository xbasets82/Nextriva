# I03.2 — Interfaz de promociones y fases

Fecha: 20/10/2026. Issue aprobado: #39. Rama: `codex/i03-2-promotions-ui`, base `c1d0126` (`main`, I03.1 integrada). Evidencia local anterior a commit; no acredita CI ni validación humana.

## Alcance y fuentes

HU03 y HU05: listado de tarjetas, detalle con URL conservada al recargar, creación/edición, fases simultáneas en orden fijo, archivo/reactivación independiente con confirmación y conservación de fases. Solo ADMIN puede acceder en I03.2; MANAGER/COLLABORATOR reciben la denegación real del backend hasta I04. No se añaden participantes, incidencias, documentos, portal comprador ni gestión formal de cambios.

Fuentes: `AGENTS.md` real; diseño funcional v1.0, §§3, 5.2, 7–9; diseño técnico v1.0; guía TDD v1.0, I03.2; contrato OpenAPI generado en `apps/web/src/api/schema.d.ts`; validaciones del backend I03.1. Se conservan nombre 3–150, descripción opcional ≤1000, ubicación opcional ≤200 y al menos una fase seleccionada. Los enums y su orden proceden del contrato existente.

Se reutilizan Card local de shadcn y Tailwind; se usa navegación hash con enlaces y sin nueva dependencia. El cliente deriva sus tipos de `operations` OpenAPI, proyecta campos públicos, envía únicamente campos admitidos y obtiene CSRF para cada mutación. La autorización efectiva permanece en servidor. Formularios, errores y confirmaciones usan castellano; no se persisten tokens en almacenamiento del navegador ni se registran respuestas privadas.

## Casos concretos y persistencia

- **Vitest, entradas inválidas:** nombre `ab`/151 caracteres, descripción de 1001 o ubicación de 201 → mensaje asociado al campo, foco y cero petición CSRF/mutación. Nombre válido sin fases → «Selecciona al menos una fase activa». No hay estado HTTP porque el formulario bloquea el envío.
- **Vitest, guardado:** nombre con espacios y `AFTER_SALES` + `PLANNING` → POST exclusivamente con nombre normalizado, descripción, ubicación y fases en orden `PLANNING`, `AFTER_SALES`; CSRF en cabecera; navegación al detalle. Edición → PATCH con sustitución de la selección por `CONSTRUCTION`.
- **Vitest, estados:** carga anunciada; listado vacío sin ejemplos; HTTP 401/403/503 → mensaje genérico y reintento; respuesta con fase desconocida → error seguro. Fallo 409 al archivar → no afirmar estado nuevo. Error 503 al guardar → conservar datos introducidos. Cancelación y navegación con cambios pendientes → confirmación; `beforeunload` cancelable.
- **Playwright, ADMIN:** login real HTTP 200; formulario inválido visible; creación mediante UI HTTP 201 con dos fases; lista → detalle; recarga; edición a Construcción + Posventa; archivo confirmado; consulta PostgreSQL comprueba `ARCHIVED` y las dos filas de fases conservadas; reactivación comprueba `ACTIVE`. Vista de 390×844 sin desbordamiento horizontal.
- **Playwright, MANAGER y COLLABORATOR:** GET real HTTP 403 y ausencia de controles/datos de promociones; POST directo con CSRF real HTTP 403; consulta PostgreSQL por nombre sintético único → cero filas. Se evita usar recuentos globales que podrían cambiar por otras pruebas concurrentes.

Vitest usa respuestas controladas para probar la interfaz; no demuestra integridad de PostgreSQL. Playwright emplea Chromium, API NestJS y PostgreSQL reales con datos sintéticos. El runner crea una base temporal aleatoria, aplica desde cero las tres migraciones versionadas existentes y la elimina al finalizar. No recibió `DATABASE_URL` de desarrollo y no se imprimieron secretos de `.env.local`.

No se afirma cumplimiento OWASP global. No se cambian logs, credenciales, autenticación ni dependencias; una nueva auditoría remota de dependencias no forma parte del delta.
- Calidad y contrato: controles de tabla superados; OpenAPI/cliente verificado sin modificación HTTP. ## Validación manual exacta

Requiere una base **local sintética ya provisionada** con migraciones de I03.1 y cuentas de prueba; estos pasos no autorizan aprovisionamiento ni migraciones adicionales. Las siguientes órdenes manuales no fueron ejecutadas contra la base de desarrollo durante esta microfase.

1. Tras `mise exec -- pnpm build`, arrancar API en una terminal desde la raíz:
   `NODE_ENV=development PORT=4317 AUTH_ORIGIN=http://127.0.0.1:5173 AUTH_LOCAL_HTTP=true mise exec -- node --env-file=.env.local apps/api/dist/src/main.js`.
2. En otra terminal: `API_PROXY_TARGET=http://127.0.0.1:4317 mise exec -- pnpm --filter @nextriva/web dev --host 127.0.0.1 --port 5173 --strictPort`.
3. Abrir `http://127.0.0.1:5173/#/promotions` con una sesión ADMIN local válida. La pantalla de login no se incorpora en I03.2. Si se necesita establecer la sesión desde la consola del navegador, usar credenciales sintéticas locales mediante `fetch('/api/auth/login', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ email: prompt('Email sintético local'), password: prompt('Contraseña sintética local') }) }).then(response => response.status)`; esperar 200 y recargar. No copiar credenciales en código ni evidencias.
4. Crear «Promoción manual sintética». Probar primero `ab` y ninguna fase: comprobar errores y foco. Completar nombre válido, descripción/ubicación opcionales y dos fases; guardar y comprobar detalle/URL y orden. Recargar y volver al listado.
5. Editar, sustituir selección por Construcción + Posventa y guardar. Archivar tras confirmar: comprobar Archivada, fases conservadas y ausencia de Editar. Reactivar y comprobar Activa. Probar Cancelar/Escape y navegación con campos sin guardar.
6. Repetir consulta con sesión MANAGER y COLLABORATOR: mensaje de permiso denegado y GET `/api/promotions` 403 en red, sin datos/controles. Sin sesión, 401. Validar teclado, foco, móvil y lectura de mensajes.

No se declara validación humana realizada. El siguiente incremento requiere una nueva instrucción del usuario.
