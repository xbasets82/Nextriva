## Decisiones aprobadas implementadas

- Campos: promoción, fase de origen, título, descripción, categoría, prioridad, autor, estado, versión, código público y fechas. Validación de servidor para UUID, longitud, campos admitidos y enums; no se aceptan campos de servidor enviados por cliente.
- La fase de origen usa el enum global aprobado: `PLANNING`, `COMMERCIALIZATION`, `EXECUTIVE_PROJECT`, `CONSTRUCTION`, `PRE_HANDOVER`, `HANDOVER`, `AFTER_SALES`. Tanto una fase activa como una fase válida no activa se aceptan. No se exige fila ni FK en `promotion_phases`; la fase desconocida u omitida se rechaza con HTTP 400 y cero persistencia. Cambios posteriores de fases activas no alteran el origen guardado.
- Categorías cerradas: `STRUCTURE`, `ENVELOPE`, `INSTALLATIONS`, `FINISHES`, `CARPENTRY`, `COMMON_AREAS`, `CLEANING`, `SAFETY`, `OTHER`.
- Prioridad: `LOW`, `MEDIUM`, `HIGH`. Estados: `OPEN`, `IN_PROGRESS`, `PENDING_VALIDATION`, `CLOSED`; `OPEN` representa **Abierta** y es el estado inicial.
- Se genera el código público con secuencia PostgreSQL global, formato mínimo `INC-000001`, sin `MAX + 1`; los huecos tras rollback están permitidos.
- Incidencia y actividad inicial `CREATED` se escriben en la misma transacción PostgreSQL. Actor y fecha se derivan en el servidor. La actividad captura `changes.originPhase`. Un fallo al insertar actividad revierte la incidencia.
- Se reutiliza el perímetro de promoción de I04. ADMIN tiene ámbito global; MANAGER y COLLABORATOR necesitan vínculo activo. La promoción archivada no admite creación. Las consultas directas ocultan recursos no visibles. I08.1 conserva comentarios y el resto de eventos/historial.
- Se añadió UI mínima para crear y abrir el detalle inmediatamente, incluida validación y feedback accesibles, sin implementar comentarios ni gestión posterior.

## Revisión de seguridad, alcance y pendientes

- Integración verificó actor y vínculo en servidor, 401 sin sesión, 403/404 de acuerdo con visibilidad, rechazo de promoción archivada, ausencia de inserts en denegaciones y fallo de actividad con rollback. También verificó unicidad de código con cuatro creaciones concurrentes, FK y unicidad de código en PostgreSQL real.
- `nextriva_dev` quedó fuera de pruebas automatizadas. El harness de E2E usa puertos alternativos sin detener procesos locales existentes.
- Durante la validación manual de la UI, el usuario autorizó aplicar la migración versionada `20261022210000_incident_creation` a `nextriva_dev` para resolver el 503 por esquema pendiente. `prisma migrate deploy` finalizó con código 0 y `prisma migrate status` confirmó después que el esquema estaba actualizado. No se creó una incidencia sintética en esa base.
- No se cambiaron los mecanismos de sesión, cookies o CSRF; CSRF se mantiene en POST. No se registran contraseñas ni tokens en evidencia.
- El esquema conserva FKs restrictivas, sin cascadas de borrado de negocio. No se incorporaron comentarios, asignación, estados mutables, notificaciones, documentos, portal comprador ni funcionalidades de I08.1.
- No se declara conformidad WCAG completa. VoiceOver, Safari y Firefox requieren comprobación manual. Migración manual en una base de desarrollo, creación de datos sintéticos para revisión y persistencia visible en DBeaver no se han realizado como parte de esta validación automatizada.
- Documentación actualizada en `docs/planning/I05.1-incident-creation.md` y `docs/architecture/decision-matrix.md`; las referencias históricas v1.0 se conservaron.
- La revisión independiente del diff no encontró bloqueos de publicación. La excepción `size:exception` quedó autorizada expresamente para una única PR. La validación manual completa y CI de PR siguen pendientes; la rama se publicó, pero aún no se ha creado la PR.
