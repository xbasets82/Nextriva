### Causa raíz y TDD del 401/403

El test E2E ejecutaba en paralelo peticiones autenticadas y `/api/auth/session`. La recuperación de sesión actualizaba `lastSeenAt`; el filtro de la sesión exigía además `lastSeenAt <= now`. El contrato correcto sigue siendo 401 sin sesión válida y 403 con sesión válida y rol insuficiente.

**RED observado:** `TEST_DATABASE_URL=... pnpm --filter @nextriva/api test:integration`, contra PostgreSQL temporal con migraciones aplicadas: 87/88 pasaron; falló solo `accepts an authenticated request that started before a concurrent session refresh`, con `UnauthorizedException`/401. **GREEN/refactor observado:** se eliminó el límite superior `lastSeenAt <= now` de la comprobación de sesión. Para que una petición antigua tampoco pueda retroceder la actividad persistida, el refresco usa una actualización SQL parametrizada y atómica con `GREATEST(last_seen_at, now)`, conservando revocación, cuenta activa, creación, expiración absoluta y expiración por inactividad. La integración real pasó 88/88 en 9 archivos. El test verifica tanto la aceptación de la lectura antigua como que `lastSeenAt` permanezca en el instante más reciente.

### Cambio y revisión técnica

`SessionGate` ahora usa un estado de cierre accesible al recibir un 401 durante logout. El gate desmonta de inmediato las pantallas privadas, pero bloquea la reautenticación hasta que la respuesta de logout se procese, incluida su cabecera `Set-Cookie`. Si el logout termina con error temporal después de un 401, login se habilita una vez que la petición concluye. No se modificaron backend, revocación de sesiones, CSRF/Origin, cookie, OpenAPI, roles, esquema ni migraciones.

Esta primera corrección impide la carrera dentro de una pestaña. La ampliación posterior entre pestañas se registra debajo: el estado React por sí solo no coordina la cookie compartida. VoiceOver y Safari/Firefox siguen pendientes de comprobación manual; no se declara conformidad WCAG completa.

### Ampliación aprobada: coordinación entre pestañas

La segunda prueba determinista abrió dos pestañas del mismo contexto Chromium. La primera revocó su sesión en la API, reteniendo la respuesta HTTP 204 con la cookie expirada; la segunda recibió 401 y se autenticó de nuevo. Al liberar la respuesta de logout, `GET /api/auth/session` pasó de 200 a 401: **RED funcional real, 23 pruebas superadas y una fallida, salida 1**. Este resultado confirmó que el guard local de React no podía proteger una cookie compartida entre pestañas. El usuario autorizó ampliar el Issue #43, que conserva `status:approved`.

La solución mínima coloca login y la secuencia CSRF/logout bajo el mismo bloqueo exclusivo Web Locks del origen. El bloqueo se libera cuando concluye la petición; el navegador procesa las cabeceras de cookie antes de resolver Fetch. La prueba ajustó su coordinación para observar `navigator.locks.query().pending`, sin esperas arbitrarias: mientras el logout está retenido, el login de la segunda pestaña está en cola y no emite su POST; la sesión anterior continúa dando 401. Tras liberar la respuesta, el login obtiene 200 y `GET /api/auth/session` conserva 200. La expectativa de sesión válida final se conserva.

Se añadieron primero dos pruebas Vitest de ausencia de Web Locks: login debe anunciar el motivo, enfocar el error y no enviar credenciales; logout no debe pedir CSRF ni modificar la sesión. **RED observado: 9/11 superadas y dos fallidas**, por ausencia del mensaje y bloqueo requeridos, salida 1. Tras la implementación, **GREEN: 11/11**, salida 0. Los errores aparecen mediante `role="alert"`; sin soporte no se ejecuta una transición sin coordinación. No se añadieron dependencias ni se modificaron seguridad o contratos del servidor.

La primera regresión web detectó siete pruebas existentes de cliente sin fixture Web Locks (107/114, salida 1); se añadió el fixture jsdom sin alterar sus expectativas. Typecheck detectó además el tipo genérico anidado de `LockManager.request` en TypeScript 5.9 (salida 2); se resolvió con `async/await` en el helper, sin casts ni supresiones. No son RED funcionales nuevos. El refactor conserva un único helper de coordinación en `api/auth.ts` y reutiliza los mensajes y transportes existentes.
