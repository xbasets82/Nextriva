## Alcance confirmado

Se implementó únicamente la entidad `users`, el hash/verificación de contraseñas, normalización/unicidad de email y las pruebas del esquema. Los roles persistidos son `ADMIN`, `MANAGER` y `COLLABORATOR`. No se añadieron sesiones, login/logout, CRUD HTTP, UI, registro público ni bootstrap. El primer usuario administrador y su mecanismo de inicialización quedan para una decisión posterior.

Los campos siguen el diseño técnico: `id`, `first_name`, `last_name`, `email`, `password_hash`, `role`, `is_active`, `created_at` y `updated_at`. La migración incluye únicamente `users`; `_prisma_migrations` es la tabla técnica de Prisma. Los checks de longitud de nombre y normalización se expresan en SQL porque Prisma no los modela en el esquema declarativo.

## Decisiones técnicas aplicadas

- Email: `trim()` y minúsculas antes de escribir; la base rechaza emails no normalizados y aplica unicidad. La inserción concurrente se valida contra PostgreSQL real.
- Roles: enum PostgreSQL `user_role` con los tres valores internos aprobados.
- Contraseñas: `argon2@0.45.1` fijado; PHC Argon2id con 19 MiB, dos iteraciones y paralelismo 1. OWASP recomienda como mínimo esos parámetros y pide medirlos en el entorno objetivo: [Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). El benchmark local en Node `v24.22.0` dio **17 ms** para un hash; no representa una medición de producción.
- La dependencia Argon2 está aprobada explícitamente para ejecutar su script nativo en `pnpm-workspace.yaml`; los scripts de `@prisma/engines`, `@scarf/scarf` y `prisma` permanecen bloqueados.
- El logger redacta `password_hash`/`passwordHash`; el servicio devuelve una proyección sin hash. No se añadió ninguna respuesta HTTP.
- La migración se aplica con Prisma CLI v7.9.1 mediante `prisma.test.config.ts`, que solo acepta una URL local en el puerto 5433 y con nombre `nextriva_test_i01_1_<32 hex>`. El runner crea la base temporal, aplica la migración, ejecuta integración y la elimina únicamente si confirmó que la creó. No se usa `nextriva_dev`, `migrate reset` ni `down -v`.

## Revisión independiente final — 20/10/2026

### Unicidad concurrente y error seguro

La restricción PostgreSQL `users_email_key` sigue siendo la garantía de unicidad. Se reforzó el caso de carrera para llamar al servicio con dos variantes (`Concurrent@Example.Test` y `concurrent@example.test`) en paralelo: ambas se normalizan al mismo email, se persiste exactamente un usuario y la otra operación falla con `UserUniqueConstraintError`. El mensaje no incluye email, contraseña, hash ni metadatos Prisma. El writer traduce el código Prisma `P2002` a ese error genérico; no se exponen el mensaje interno ni los metadatos del ORM.

Evidencia TDD de esta corrección:

1. **Red observado:** `mise exec -- pnpm --filter @nextriva/api exec vitest run src/users/prisma-users.writer.test.ts` — `exit 1`; el writer propagaba el objeto de error recibido y no producía una excepción segura.
2. **Green inicial:** la prueba unitaria pasó después de añadir la traducción de `P2002`.
3. **Desajuste descubierto en integración:** las primeras ejecuciones reales fallaron porque Prisma 7.9.1 con `PrismaPg` no entregó `meta.target`; solo se observó `code: P2002`. Se descartó depender de ese metadato y se traduce el código a un error genérico sin copiar el detalle original.
4. **Green final:** `mise exec -- pnpm --filter @nextriva/api test:integration` — migración aplicada en base local efímera, **13/13 pruebas**, `exit 0`. La prueba concurrente consulta PostgreSQL y confirma una sola fila.

### Política de contraseña y límites

- **Implementado:** Argon2id con `argon2@0.45.1`, memoria `19456 KiB` (19 MiB), dos iteraciones y paralelismo uno. La biblioteca genera una sal aleatoria individual; dos hashes de la misma contraseña difieren. La contraseña correcta verifica como `true` y una incorrecta como `false`. Solo se persiste el hash; la proyección omite `passwordHash` y Pino redacta `password_hash` y `passwordHash`.
- **Errores:** fallos de `hash` se propagan al llamador y no se registran. Un hash malformado puede hacer que `verify` rechace con un error de la biblioteca; no existe todavía flujo HTTP ni consumidor de autenticación en I01.1. I01.2 deberá convertir errores internos de verificación en un fallo genérico, sin devolver ni registrar hash, contraseña o detalles Argon2.
- **Pendiente de decisión:** longitud mínima/máxima y reglas de contraseña, y el mecanismo seguro de entrega inicial. No se inventan ni se aplican en I01.1.

### Alta inicial y validación de identidad

No hay bootstrap, usuario predeterminado, credencial publicada, registro público ni endpoint administrativo. El diseño técnico prevé que el bootstrap administrativo futuro sea explícito y use un secreto externo, sin ruta pública. Antes de habilitar el uso real del login deberá decidirse en un incremento posterior el mecanismo de aprovisionamiento inicial y la entrega de credenciales; I01.1 no crea ese mecanismo.

El email sí se recorta en extremos y convierte a minúsculas antes de persistir; PostgreSQL exige la forma normalizada y la unicidad. La decisión aprobada de I01.1 no definió un validador sintáctico de email. El diseño técnico menciona “email válido”, por lo que la regla concreta debe cerrarse antes de exponer la creación de usuarios en I02.1. Los checks de nombres aplican límites 2–100 y 2–150; no se inventó una regla de normalización de nombres.
