# Rediseño del listado de promociones

Fecha: 25/10/2026. Issue [#99](https://github.com/xbasets82/Nextriva/issues/99), aprobada. Rama `codex/issue-99-promotion-list-redesign`, desde `main` actualizado en `f68ec877a67859481fddc64ced4e2d83def3ca72`.

## Alcance y decisiones

HU03/HU05: búsqueda parcial por nombre o localización, con recorte de espacios exteriores e insensible a mayúsculas; filtros combinables por estado y fase; orden estable por nombre ascendente y `id` ascendente; diez promociones por página. Una promoción archivada coincide con las fases que conserva la API. Los filtros se mantienen al navegar al detalle y volver durante la misma navegación de la aplicación, sin guardarlos en URL ni almacenamiento del navegador.

El listado sigue consultando la API existente, que ya devuelve el conjunto completo autorizado para la sesión. El filtrado y la paginación son locales sobre ese conjunto; no cambia API, autorización, contratos, permisos, esquema ni dependencias. ADMIN conserva el botón de creación; MANAGER y COLLABORATOR no lo ven. Se mantienen estados de carga, error, reintento y lista vacía. La tarjeta compacta muestra nombre, localización con pin, icono de estado accesible y fases conservadas. Las siete fases proceden del catálogo existente.

### Validación complementaria: texto largo y retorno desde página 2

Se amplió el E2E con un nombre sin espacios de 150 caracteres y una localización sin espacios de 200 caracteres, ambos dentro del viewport móvil de 390 px. Antes del ajuste CSS, el runner seguro mostró desbordamiento horizontal: fallaron la aserción del listado de promociones y una aserción móvil existente de login mientras compartían la base temporal del mismo E2E. El nombre y la localización del listado ahora pueden reducir su ancho y partir cualquier palabra mediante `min-w-0` y `overflow-wrap:anywhere`. La repetición real del navegador pasó esas comprobaciones de anchura.

También se reforzaron las pruebas de vuelta desde el detalle: Vitest navega desde la segunda página, vuelve y comprueba que conserva la página 2 y la fase elegida; Playwright vuelve desde la segunda página y confirma la búsqueda, los filtros y el indicador de página. Una primera ejecución Vitest no encontró el detalle porque el mock solo respondía a otro UUID; se completó el mock, sin cambiar producción, y pasó 9/9 (código 0). Una ejecución E2E posterior a la corrección CSS encontró una expectativa del fixture que asumía cuál promoción quedaba última tras el orden alfabético; se cambió para abrir la única fila real de la página 2. La siguiente ejecución E2E completa con el runner aislado pasó 48/48 (código 0).

### Cobertura explícita de las siete fases

La prueba anterior confirmaba que el selector exponía siete opciones, pero solo ejecutaba el filtro para `HANDOVER`. Se añadió una prueba Vitest parametrizada por las siete fases existentes. Usa una promoción activa con las siete fases simultáneas y otra archivada que conserva `HANDOVER` y `AFTER_SALES`; así comprueba cada opción, que una promoción con varias fases aparece una sola vez y que las fases conservadas de una promoción archivada siguen coincidiendo. No se observó RED funcional: el filtro ya estaba implementado y el objetivo era cerrar una brecha de cobertura, por lo que la nueva prueba pasó directamente en la primera ejecución (16/16 pruebas del archivo, código 0).

En una ronda previa de comprobaciones paralelas, cobertura registró 258/259: una prueba existente de `PromotionForm.test.tsx` no encontró el botón `Crear promoción`. No se asigna una causa a ese resultado. TypeScript también detectó que el mock nuevo usaba métodos de cadena sobre el tipo `RequestInfo | URL`; se normalizó la ruta de petición con `String(path)`. Las repeticiones seriales pasaron: unitarias 259/259, cobertura 259/259 (95,11 % líneas, 89,72 % ramas, 93,53 % funciones y 93,27 % sentencias), typecheck, lint, formato y build (todos código 0). La suite E2E final posterior a las modificaciones pasó 48/48 con PostgreSQL temporal aislado.
