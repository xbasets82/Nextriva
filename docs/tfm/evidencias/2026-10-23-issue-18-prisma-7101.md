## Objetivo y decisión

Retirar del baseline las tres excepciones Prisma temporales sin overrides y conservar PostgreSQL como único adaptador de base de datos de la aplicación.

Se fijaron `prisma`, `@prisma/client` y `@prisma/adapter-pg` en `7.10.1`. El adaptador también se actualizó para mantener alineadas las versiones de los paquetes Prisma instalados directamente; su configuración PostgreSQL y el esquema no cambiaron. Prisma 7.10.1 requiere Node `^20.19`, `^22.12` o `>=24.0`, por lo que el Node 24.22.0 fijado por Nextriva es compatible. [Notas de Prisma ORM 7.10.1](https://github.com/prisma/orm/releases) · [Requisitos de Prisma ORM 7](https://www.prisma.io/docs/orm/v7/reference/system-requirements)

Las versiones efectivas del lockfile son `mysql2@3.24.4` y `deepmerge-ts@8.0.2`, superiores a las versiones corregidas publicadas para los avisos de este issue:

## Evidencia TDD observada

El comportamiento funcional de Nextriva no cambia; para esta corrección de dependencias, la auditoría del lockfile es la comprobación de seguridad principal.

### Red

- Antes de la actualización, `pnpm audit --json` terminó con código **1** y mostró exactamente los tres GHSA anteriores: dos altos y uno moderado. No se detectaron otros avisos.
- Se añadieron primero dos pruebas: el baseline real no debe contener esas excepciones y el evaluador debe rechazar su reintroducción.
- `mise exec -- pnpm test:audit-baseline`: **35 aprobadas, 2 fallidas; código 1**. Ambas fallaron por las excepciones activas en `.github/audit-baseline.json` y porque el evaluador aún las aceptaba. Es el RED observado; no se reconstruye evidencia histórica.
- Durante la preparación del commit, ESLint señaló que una colección de aprobaciones vacía podía representar un control frágil. Se añadió una expectativa que requiere un rechazo explícito cuando el baseline contiene cualquier excepción; el RED falló porque el mensaje aún solo clasificaba excepciones individuales como no aprobadas.

### Green

- `mise exec -- pnpm install --lockfile-only --ignore-scripts`: código **0**; lockfile regenerado con pnpm 10.34.7.
- La auditoría del lockfile tras resolver Prisma 7.10.1 encontró **0 avisos; código 0**.
- Se vació el baseline y se cambió el evaluador para rechazar cualquier lista de excepciones no vacía; no depende de una colección vacía ni conserva autorizaciones implícitas. Las pruebas bloquean los tres GHSA si reaparecen, así como cualquier excepción futura no aprobada.
- `mise exec -- pnpm test:audit-baseline`: **24 aprobadas, 0 fallidas; código 0**. Las pruebas exigen un informe válido, códigos coherentes, rechazo de hallazgos no aprobados y ausencia total de excepciones.

### Refactor y revisión

- No se modificaron reglas de autorización, API, esquema Prisma ni migraciones.
- Se mantuvo el control estricto del baseline; los tres GHSA ya no están permitidos ni en el JSON ni en la lista de aprobaciones del evaluador.
- En el primer hook pre-commit, ESLint detectó la colección vacía y detuvo el commit; no se omitió el hook. Tras la corrección, Prettier se aplicó al test del baseline y se repitieron las comprobaciones.

## Incidencias de ejecución y límites

- La primera ejecución unitaria, lanzada simultáneamente con otras comprobaciones, tuvo un fallo de foco en una prueba web de comentarios: esperaba el foco en el campo y encontró el encabezado. La prueba aislada pasó **32/32** y la suite completa repetida pasó **360/360**. No se modificó la aserción ni el código web; se conserva el fallo inicial como intermitencia observada.
- El primer arranque E2E no pudo iniciar Playwright porque el puerto predeterminado 4317 estaba ocupado por un proceso de Node del checkout. No se detuvo ese proceso. Se repitió usando los puertos alternativos soportados por `playwright.config.ts`; entonces pasaron las 32 pruebas.
- No se usó `nextriva_dev` en pruebas. Ninguna migración se ejecutó sobre esa base ni se modificaron sus datos. La prueba de integración y E2E usó el runner existente con `DATABASE_URL` y `TEST_DATABASE_URL` heredadas desactivadas y una base temporal PostgreSQL.
- No se alteraron `schema.prisma` ni archivos de migraciones; no hubo cambios funcionales ni de contrato OpenAPI.
- No se ejecutó CI remoto. Quedan pendientes revisión humana y decisión posterior sobre commit/publicación.
