# Evidencia — I10.2: artefacto y datos de demo

Fecha: 27/10/2026. Issue [#138](https://github.com/xbasets82/Nextriva/issues/138), aprobado; rama `codex/i10-2-demo-artifact`, desde I10.1 integrada (`942a772`). Preparación local, sin despliegue ni uso de `nextriva_dev`.

## Decisiones implementadas

Proyecto Compose `nextriva-demo`, base `nextriva_demo`, modo `AUTH_DATABASE_MODE=demo`, archivos privados de runtime/migración/seed y perfiles de mantenimiento explícitos. Se conservan esquema, migraciones, entidades y contratos HTTP. No hay dependencias nuevas ni cambios de baseline.

El seed requiere marcador administrativo previo `nextriva:demo:ready:v1` y ausencia de filas en las ocho tablas. Bloquea esas tablas y, en una única transacción, crea usuarios de los tres roles, una promoción, participantes, una incidencia y su actividad inicial; consume el marcador convirtiéndolo en `initialized`. Argon2id conserva los parámetros existentes. El comando exige confirmación y credenciales externas distintas; rechaza CI/test/destinos ambiguos. El administrador es privado y no se expone en el flujo de demo.

`/api` y `/api/*` se encaminan a la API; el fallback SPA queda en el manejador web. El proxy sobrescribe `X-Forwarded-For`. La API solo usa una IP reenviada válida desde un peer configurado explícitamente; no activa confianza global ni CORS. La validación local usa build de Vite y API empaquetada, Caddy, HTTPS con certificado efímero fijado por SPKI y PostgreSQL tmpfs. No acredita DNS ni TLS públicos.

## Fallos y comprobaciones pendientes

Los dos primeros intentos del runner de producción terminaron antes de Playwright con salida 1 porque el harness publicaba el proxy únicamente en una red Docker `--internal`. Una comprobación efímera real mostró `Ports: {80/tcp:[]}`; al conectar una red ingress apareció un puerto `127.0.0.1`. Se separaron base interna e ingress como en el Compose existente. La ejecución final posterior completó el recorrido; no se cambiaron las aserciones HTTP, TLS ni de negocio. Consultas posteriores de contenedores y redes con la etiqueta propia de sesión devolvieron cero remanentes.

La primera ejecución del E2E habitual, simultánea a cobertura, falló antes de tests con `EEXIST` al regenerar Prisma en el mismo checkout. Fue un error de coordinación de la validación; no se modificaron las salidas generadas ni se debilitó el runner. El intento secuencial iniciado después también terminó antes de tests: el servicio local existente ocupaba `4317/api/health`. No se cerraron servicios ajenos ni se modificó `reuseExistingServer:false`. La repetición final secuencial con puertos libres pasó 77/77.

Tras estos incidentes se pausaron builds y pruebas para revisión fresca. Un intento adicional de producción fue interrumpido antes de Playwright con SIGTERM (salida 1); el rerun final posterior pasó. En la revisión de seguridad se detectó que cuatro llamadas de limpieza Docker heredaban `process.env` en vez del entorno de Docker validado. La regresión RED/GREEN queda registrada arriba; la limpieza usa ahora el mismo entorno aislado que la creación. Logs locales conservados fuera de Git en `/tmp/nextriva-i102-*.log`.

Pendiente: validación humana del resultado y de cualquier futura configuración pública de demo. No se hizo despliegue. VoiceOver, Safari y Firefox no ejecutados; la UI no cambió y no se afirma conformidad WCAG completa ni validación visual humana.
