# Issue #163 — Seguridad de publicación y despacho automático

## Resultado local

La primera parte endurece el workflow de publicación manual existente: el gate solo acepta `expected_sha=current` para el actor automatizado esperado; una persona debe aportar el SHA estable explícito. Si GHCR ya contiene la etiqueta del commit, el cliente verifica el paquete y su revisión OCI y reutiliza el digest; no reconstruye ni mueve la etiqueta. La publicación y el rollback comparten el grupo `nextriva-public-deployment` con `queue: max`, de modo que una ejecución pendiente no sustituye a otra. El helper del VPS conserva el bloqueo exclusivo y la protección de `runId` como verificaciones finales.

La segunda parte añade un workflow `workflow_run` que escucha el CI completado de `main` y solicita el `workflow_dispatch` de despliegue ya existente. Solo actúa cuando `NEXTRIVA_CD_AUTO_ENABLED=true` y `NEXTRIVA_CD_MANUAL_ENABLED=true`; estas variables no se configuraron ni modificaron. El CD automático permanece apagado. No se ejecutó despliegue, rollback, publicación GHCR ni operación en VPS.

El despachador valida mediante API el repositorio, nombre y ruta del CI, el evento `push`, rama `main`, estado/conclusión, SHA que sigue siendo HEAD y cada uno de los seis jobs requeridos. El token del job tiene `contents:read` y `actions:write`, sin permisos de paquetes ni secretos SSH. El workflow de despliegue vuelve a validar el SHA y el CI. El dispatcher usa su propio grupo; publicación y rollback comparten `nextriva-public-deployment` con `queue: max`. GitHub limita la espera a 100 ejecuciones y no garantiza FIFO. No se cambiaron operaciones de PostgreSQL.

## Pruebas observadas

- **RED de reuso:** `node --test --test-name-pattern='reintentar un SHA publicado' scripts/cd-client.test.mjs` falló en `digest_output_invalid`; el cliente no reutilizaba ni verificaba etiquetas existentes.
- **RED de política/gate:** falló al permitir el `expected_sha=current` humano y al no aceptar ese marcador restringido al deploy automático.
- **RED de dispatcher:** falló por ausencia de `assertWorkflowRun`, `scripts/cd-auto.mjs` y `.github/workflows/auto-deploy.yml`.
- **RED de cola:** la regresión falló al no encontrar `queue: max`; una ejecución pendiente podía sustituir otra.
- **GREEN aislado PR1:** `mise exec -- pnpm test:cd` pasó **203/203** y `mise exec -- pnpm test:cd:postgres` pasó **1/1** en PostgreSQL temporal.
- **GREEN conjunto PR1+PR2:** `mise exec -- pnpm test:cd` pasó **207/207** (código 0) y `mise exec -- pnpm test:cd:postgres` pasó **1/1** (código 0) en PostgreSQL temporal.
- ESLint, Prettier `--check` y `git diff --check` pasaron. `actionlint 1.7.12` no reconoce `concurrency.queue`; se usó un ignore exacto para esa clave documentada por [GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency). GitHub CI debe validar el workflow.

Las ejecuciones válidas usaron `mise exec` con Node `24.22.0` y pnpm `10.34.7`. El lint inicial detectó complejidad y ternarios anidados; se extrajeron operaciones pequeñas y se repitió con éxito.

## Límites y riesgos pendientes

- GHCR no impide que un operador con permiso de escritura mueva manualmente una etiqueta; el pipeline rechaza una revisión OCI distinta y el acceso de escritura debe seguir limitado.
- La integración con PostgreSQL temporal no es una prueba contra producción. Typecheck, build de aplicación, OpenAPI, E2E de producto y auditoría no aplican al cambio de infraestructura.
- La protección depende de las reglas de rama, permisos de paquetes y secretos SSH existentes; no se modificaron. GitHub CI debe validar el workflow antes del merge.
- El CD automático sigue apagado hasta que se autorice/configure `NEXTRIVA_CD_AUTO_ENABLED` y se valide el primer disparo automático.
