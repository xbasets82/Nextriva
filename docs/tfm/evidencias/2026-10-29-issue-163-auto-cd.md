# Issue #163 — Seguridad de publicación y reintentos (PR 1/2)

## Resultado local

La primera parte endurece el workflow de publicación manual existente: el gate solo acepta `expected_sha=current` para el actor automatizado esperado; una persona debe aportar el SHA estable explícito. Si GHCR ya contiene la etiqueta del commit, el cliente verifica el paquete y su revisión OCI y reutiliza el digest; no reconstruye ni mueve la etiqueta. La publicación y el rollback comparten el grupo `nextriva-public-deployment` con `queue: max`, de modo que una ejecución pendiente no sustituye a otra. El helper del VPS conserva el bloqueo exclusivo y la protección de `runId` como verificaciones finales.

No se cambiaron operaciones de PostgreSQL. No hubo publicación, despliegue, rollback ni cambios remotos.

## Pruebas observadas

- **RED:** `node --test --test-name-pattern='reintentar un SHA publicado' scripts/cd-client.test.mjs` falló en `digest_output_invalid` porque el cliente no reutilizaba/verificaba una etiqueta ya publicada.
- **RED:** el caso del gate falló al permitir que un dispatch humano usara `expected_sha=current`.
- **GREEN del cambio completo en el árbol local:** `mise exec -- pnpm test:cd` pasó **207/207** y `mise exec -- pnpm test:cd:postgres` pasó **1/1**; la segunda prueba usó PostgreSQL temporal.
- ESLint y Prettier pasan. GitHub documenta `concurrency.queue: max`; `actionlint 1.7.12` aún lo marca como clave desconocida, así que se ejecutó con una excepción exacta para ese falso positivo y validó el resto de la sintaxis. CI de GitHub debe confirmar la validación del workflow.

El árbol local también contiene la segunda parte de la Issue (dispatcher automático); estos conteos incluyen ambos incrementos y se volverán a medir por PR.
