## Decisiones aprobadas

ADMIN consulta globalmente y gestiona participantes de cualquier promoción. MANAGER y COLLABORATOR consultan solo promociones a las que están vinculados; el acceso directo a otra promoción debe devolver 404. MANAGER solo puede gestionar COLLABORATOR en su promoción; una acción prohibida en una promoción visible devuelve 403. El rol pertenece a `users`, sin rol adicional por promoción.

Una nueva vinculación exige un usuario activo y una promoción activa; una vinculación duplicada devuelve 409. Una promoción archivada impide nuevas vinculaciones, pero permite retiradas autorizadas para revocar accesos. La retirada debe conservar usuario, promoción y autoría histórica. La futura integración con incidencias debe impedir retirar responsables con incidencias abiertas o dejar pendientes sin validador elegible.

Inicialmente, la comprobación del entorno solo informó presencia/ausencia, sin revelar valores: `TEST_DATABASE_URL` no estaba disponible y `.env.test.local` todavía no existía; tampoco se utilizó `DATABASE_URL`. Después se configuró `.env.test.local` con permisos privados. El diagnóstico confirmó que el contenedor reutilizaba un volumen ya inicializado y que sus variables actuales no prueban las credenciales históricas; no se reinicializó el volumen ni se cambió contraseña. La persona usuaria informó una ejecución de 9 archivos y 88 pruebas superadas. Posteriormente, el runner seguro se ejecutó aquí contra bases PostgreSQL temporales aisladas. No se leyó ni cargó `.env.local`, no se heredó `DATABASE_URL` y no se usaron datos de `nextriva_dev`.

## Seguridad y Definition of Done

- El backend revalida actor, vínculo y elegibilidad. Las consultas filtran por vínculo en PostgreSQL; las mutaciones coordinan el bloqueo de promoción con las altas/bajas y cambios de estado.
- La respuesta de participantes usa una proyección permitida y omite hashes, cookies y tokens. CSRF continúa requerido en las rutas mutantes.
- No se han cambiado cookies, sesiones, CSRF ni controles criptográficos. No se ha accedido ni modificado `nextriva_dev`.
- FKs, unicidad, ausencia de cascada, rollback de inserción fallida, alta duplicada concurrente y denegaciones sin mutación se verificaron en PostgreSQL temporal real. No existe todavía el modelo de incidencias para probar responsables con incidencias abiertas.
- UI y validación de accesibilidad de participantes corresponden a I04.2. VoiceOver y Safari/Firefox siguen pendientes manuales del proyecto; no se afirma conformidad WCAG completa.
- Incidencias/validadores: no aplicable a la implementación presente porque ese modelo aún no existe; dependencia obligatoria antes de incorporarlo.
- OpenAPI y tipos: se añadieron GET/POST/DELETE de participantes y `api:types:check` pasó. No se añadió UI ni lógica cliente de I04.2.
- Cobertura: pasan los umbrales del runner (80 % líneas, 75 % ramas). `src/promotions` tiene 94,19 % líneas y 81,87 % ramas; queda bajo el objetivo aspiracional del 90 % para ramas de dominio. No se rebajaron umbrales.

- VoiceOver/Safari/Firefox no aplican a este incremento backend. La restricción de retirada de responsables con incidencias abiertas queda pendiente de integrar antes de I05.
- DoD: persistencia, autorización, contrato y E2E pasan localmente. **La evidencia TDD no cubre RED previo para cada ruta de alta/baja**, como se documenta arriba; por ello no se marca I04.1 como cerrado/completado.
