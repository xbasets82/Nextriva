## Alcance y decisiones aplicadas

Se implementa `POST /api/auth/logout`. El `SessionGuard` existente valida la cookie, el origen y el CSRF; para logout autentica sin modificar la actividad. El servicio deriva SHA-256 del token opaco y PostgreSQL revoca condicionalmente la sesión activa en una sola actualización. Solo después de una revocación confirmada, el controlador responde `204` sin cuerpo y caduca la cookie con el mismo nombre y atributos de seguridad.

| Situación                                               |                      Respuesta | Efecto persistido / cookie                                      |
| ------------------------------------------------------- | -----------------------------: | --------------------------------------------------------------- |
| Sesión válida, CSRF y origen válidos                    |                204, sin cuerpo | `revokedAt` se establece; cookie se caduca                      |
| Cookie ausente, inválida, expirada, inactiva o revocada |                            401 | Sin nueva mutación ni cookie de logout                          |
| CSRF ausente/inválido u origen no permitido             |                            403 | Sin cambios en `revokedAt`/`lastSeenAt`; sin `Set-Cookie`       |
| Logout repetido o carrera concurrente                   | 401 tras una revocación válida | Como máximo una solicitud obtiene 204; la fila termina revocada |

No se añadió entidad, migración, dependencia, CRUD de usuarios, interfaz de logout ni flujo de I02. `revokeSessionsForUser(transaction, userId, now)` queda disponible para ejecutarse en la misma transacción que un cambio de estado/rol futuro. La prueba usa actualizaciones sintéticas del usuario; aún no existe un flujo de gestión de usuarios de producción que la invoque. Si falla esa transacción, se revierten tanto el cambio como las revocaciones.

La cookie secure de producción conserva `__Host-nextriva_session`, `Path=/`, `HttpOnly`, `Secure`, `SameSite=Lax`, sin `Domain`, `Max-Age=0` y fecha expirada. La configuración local HTTP caduca `nextriva_session` sin `Secure`, igual que la cookie local ya emitida.

## Revisión final: carrera entre validación y revocación

En la revisión previa a publicación se detectó que `SessionGuard` autenticaba el logout mediante `consumeSession`, que actualizaba `lastSeenAt`, antes de que el servicio intentara revocar. Si la expiración absoluta ocurría entre ambas operaciones, o si otra solicitud revocaba primero, el logout podía responder 401 dejando `lastSeenAt` modificado. La primera prueba de concurrencia anterior comprobaba el estado final revocado, pero no protegía este campo; el reloj fijo no exponía la ventana temporal.

Se corrigió el fixture para que la sesión estuviera activa en el primer instante y exactamente expirada en el segundo; no se cambió producción para obtener el RED.

### GREEN y REFACTOR

- `SessionGuard` sigue validando cookie, CSRF y origen, pero la ruta logout lleva metadatos para que la autenticación consulte la sesión sin actualizar `lastSeenAt`. Las demás rutas mantienen `refreshActivity: true` por defecto.
- `revokeSession` aplica una sola actualización condicional de PostgreSQL con sesión no revocada, usuario activo, `createdAt <= now`, `expiresAt > now` y `lastSeenAt > now - 30 minutos`. La sentencia decide y revoca atómicamente; al llegar al límite exacto o perder una carrera, afecta cero filas, responde 401 y no escribe `lastSeenAt` ni `revokedAt`. La cookie solo se caduca después de una revocación confirmada.
- El REFACTOR extrajo `activeSessionWhere` para compartir exactamente el mismo predicado de vigencia entre la consulta de autenticación y la revocación; evita que ambas rutas diverjan en límites.
- Integración PostgreSQL después de la solución: `mise exec -- pnpm --filter @nextriva/api test:integration` — 5 archivos, 30/30 pruebas, código 0. Incluye expiración absoluta exacta, límite de inactividad, concurrencia `[204, 401]`, `lastSeenAt` intacto para la solicitud rechazada y CSRF/origen con estado y cookie intactos.
- Unitarias del guard: `mise exec -- pnpm --filter @nextriva/api exec vitest run src/auth/session.guard.test.ts` — 4/4, código 0; verifica que únicamente la ruta marcada omite el refresh y que el comportamiento normal sigue activo.
