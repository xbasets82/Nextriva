# Evidencia I01.2 — Login y sesiones persistentes

**Fecha:** 20/10/2026

**Rama:** `codex/i01-2-login-sessions`

**Estado:** implementación y validación local; pendiente de revisión humana y autorización para commit, push y PR. No existe commit de I01.2 al redactar esta evidencia.

## Alcance, fuentes y autorización

HU01, limitada a login y consulta de sesión. Se consultaron `AGENTS.md`, diseño funcional §§4–7, diseño técnico §§4–5 y la guía original I01.2/I01.3. El usuario aprobó las políticas y autorizó el desarrollo y esta evidencia tras su incorporación al Issue #23. La guía reserva **logout y revocación explícita por cierre de sesión a I01.3**; no se implementan en esta microfase.

Se añaden únicamente `POST /api/auth/login`, `GET /api/auth/session` y `GET /api/auth/csrf`. Sin registro público, bootstrap, usuario predeterminado, recuperación por email, CRUD de usuarios ni pantallas de negocio. La ruta mutante usada para probar el guard existe exclusivamente en el módulo de integración, nunca en la aplicación entregada. No se añaden dependencias ni se modifica el lockfile.

## Decisiones y separación de responsabilidades

| Responsabilidad | Implementación y decisión aprobada                                                                                                                                                                                                                                                                                                                   |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP y OpenAPI  | `AuthController` traduce entrada/salida, valida una lista cerrada de campos, publica DTO seguros y emite la cookie. Login devuelve 200; petición inválida 400; credenciales inválidas 401; origen/CSRF 403; límite 429; infraestructura no disponible 503 genérico.                                                                                  |
| Autenticación   | `AuthService` normaliza email y verifica Argon2id usando el hasher de I01.1. Usuario inexistente usa un hash ficticio aleatorio de igual configuración; inactivo y contraseña errónea no crean sesión. Fallos de verificación se convierten en rechazo genérico; fallos de infraestructura no exponen detalles.                                      |
| Sesiones        | Token CSPRNG de 32 bytes, codificado base64url. Solo SHA-256 en PostgreSQL; UUID interno independiente. Cada login genera secreto nuevo y revoca atómicamente la sesión previa presentada del mismo usuario, para evitar fijación. Esto no incorpora el endpoint de logout de I01.3.                                                                 |
| Expiración      | Máximo absoluto de 8 horas; inactividad de 30 minutos. Comparaciones estrictas: en el instante exacto del límite la sesión deja de ser válida. Reloj inyectado en pruebas, sin esperas. La actividad actualiza `last_seen_at` solo si la sesión sigue válida y el usuario activo; nunca extiende `expires_at`.                                       |
| Persistencia    | `PrismaAuthStore` consulta usuario actual y administra exclusivamente `sessions`; las transacciones coordinan creación/rotación y comprobación/actualización de actividad. No se confía en roles almacenados en la cookie.                                                                                                                           |
| Cookies         | HTTPS: `__Host-nextriva_session`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, sin `Domain`, máximo 28.800 segundos. Desarrollo HTTP explícito en loopback y `NODE_ENV=development`: `nextriva_session`, sin Secure. El nombre local es diferente porque el prefijo `__Host-` exige Secure en navegadores. La excepción se rechaza en producción. |
| CSRF            | Derivación HMAC-SHA-256 con el secreto de sesión y contexto fijo; comprobación constante y token distinto para cada sesión. `GET /api/auth/csrf` entrega exclusivamente ese token derivado. El guard exige `X-CSRF-Token` y origen válido en métodos mutantes autenticados. Login usa la protección de origen aprobada sin exigir una sesión previa. |
| Origen          | `Origin` debe coincidir exactamente con el origen canónico configurado. Solo si falta se permite `Referer` cuyo origen coincida; se rechazan ausencia, `null`, origen extranjero, credenciales en URL y valores malformados. No se configura CORS permisivo.                                                                                         |
| Intentos        | Cinco fallos por email normalizado + IP en ventana móvil de 15 minutos; siguiente intento 429 genérico. Se serializan intentos concurrentes de la misma combinación para que no eludan el límite. Los registros caducados se eliminan al consultar.                                                                                                  |
| Logs            | Se reutiliza Pino y el middleware de I00.5. No se registran cuerpos, cookies, tokens, hashes ni contraseñas. Pruebas capturan logs en memoria y comprueban la ausencia de los valores sintéticos y la ruta parametrizada/status reales.                                                                                                              |

Referencias oficiales consultadas el 20/10/2026: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) y [Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). Son referencias para controles concretos; esta evidencia no acredita una certificación OWASP.

## Migración y aislamiento PostgreSQL

`20261020100000_sessions/migration.sql` añade exactamente `sessions`: `id`, `user_id`, `token_hash`, `created_at`, `last_seen_at`, `expires_at`, `revoked_at`. FK real a `users` con `ON DELETE RESTRICT`; hash único de 64 caracteres hexadecimales; fechas UTC/TIMESTAMPTZ; checks cronológicos e índice usuario/expiración. No se modifica la migración de I01.1 ni se añaden otras entidades.

El harness existente crea una base vacía `nextriva_test_i01_1_<32 hex>` exclusivamente en el PostgreSQL local de pruebas (5433), aplica ambas migraciones y elimina solo la base aleatoria que confirmó haber creado. Se conserva el prefijo histórico del harness para reutilizar su validación restrictiva. No se ejecutan migraciones contra `nextriva_dev`, `migrate reset` ni `down -v`; no se eliminan volúmenes.

El mismo harness se reutiliza para integración, cobertura API y E2E. El modo runtime `AUTH_DATABASE_MODE=isolated-test` exige entorno development/test y la URL temporal validada; producción rechaza ese modo. Playwright gestiona API, Vite y Chromium, sin reutilizar servidores manuales. No hay seeds permanentes: los usuarios sintéticos se crean solo en la base temporal, con contraseñas aleatorias en memoria.

## Reproducción manual y configuración

Para reproducir las verificaciones sin crear usuarios en desarrollo:

1. Desde la raíz, ejecutar `mise exec -- pnpm --filter @nextriva/api test:integration`: debe aplicar ambas migraciones en una base temporal y superar 25 pruebas.
2. Ejecutar `mise exec -- pnpm --filter @nextriva/api test:e2e`: debe superar cuatro pruebas y limpiar su base temporal. Se usan Chromium y la API real; ninguna API está interceptada por mocks.
3. Para observar Chromium/Inspector de forma interactiva: `mise exec -- env PWDEBUG=1 pnpm --filter @nextriva/api test:e2e`. Esta modalidad es una instrucción para validación humana, **no se ha ejecutado en esta evidencia**; mantener libre 4317/5173 y cerrar el inspector al terminar.
4. Revisar la migración SQL y los esquemas en `/api/docs-json` del servidor levantado por las pruebas. La configuración de OpenAPI del servidor de desarrollo sigue en `main.ts`; no hay publicación externa.

Configuración runtime: `AUTH_ORIGIN` debe ser un origen canónico HTTPS; HTTP solo se acepta con `AUTH_LOCAL_HTTP=true`, `NODE_ENV=development` y host loopback. Sin configuración válida, autenticación falla con 503 genérico mientras health continúa disponible. Las URLs de base de datos se leen del entorno y nunca se imprimen. El runner carga `.env.local` ignorado y valida destino antes de conectar.

No se ha migrado la base de desarrollo y no existe usuario inicial ni pantalla de login en esta microfase. Un login manual fuera del entorno de prueba requiere autorización independiente para preparar su base/usuario; esta evidencia no introduce un bootstrap ni credenciales por defecto.

## Limitaciones, DoD y siguiente revisión

- El contador de intentos vive en un proceso, se pierde al reiniciarlo y no se comparte entre instancias. No impone bloqueo de cuenta; el transporte usa IP del socket y no confía en `X-Forwarded-For`. Un proxy desplegado requerirá política explícita y revisada. Muchas identidades distintas pueden aumentar consumo de memoria dentro de la ventana; revisar antes de despliegue público.
- Logout, revocación por cambios de privilegios/contraseña y flujo UI de acceso quedan para las microfases correspondientes. Un usuario inactivo o sesión con `revoked_at` ya es rechazado al consultarse; no se atribuye una API de gestión/revocación a I01.2.
- El token CSRF derivado está ligado al secreto de sesión y no requiere campo/entidad adicional. La fixture mutante comprueba protección real sin añadir endpoints de negocio.
- Transporte HTTPS y proxy de producción no se han desplegado ni probado en navegador HTTPS; sí se prueban atributos/configuración secure y la excepción local. UI responsive/accesibilidad no aplica a nuevas pantallas porque no se cambia frontend; la pantalla inicial se ejecuta como regresión.
- Sin pruebas de permisos por promoción/incidencia, porque pertenecen a incrementos posteriores. No se modifica auditoría de negocio. Integridad y ausencia de efectos se comprueban para las operaciones de autenticación de esta microfase.
- No se ha ejecutado CI remota, ni commit, push, PR o merge. Los resultados de GitHub Actions de una futura publicación siguen N/D.
- Verificación de secretos limitada al diff/archivos de entrega, a artefactos ignorados y a pruebas de logs/respuestas; no se leen secretos locales ni se atribuye una auditoría de penetración completa.

**Conclusión local:** criterios del Issue #23 verificados; preparado para revisión humana previa al commit. La aprobación/publicación requiere nueva autorización expresa del usuario.
