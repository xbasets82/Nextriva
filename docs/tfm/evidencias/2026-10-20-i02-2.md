## Decisiones y archivos

- Tipos generados con `openapi-typescript@7.10.1`, fijado como dependencia de desarrollo y lockfile. Licencia MIT, peer TypeScript `^5.x`; documentación oficial recomienda Node 20 o posterior. Se usa Node 24/TypeScript 5.9.3 del proyecto. No se incorpora cliente HTTP de ejecución: se usa `fetch`. Fuentes: [introducción oficial](https://openapi-ts.dev/introduction) y [manifiesto de la versión fijada](https://github.com/openapi-ts/openapi-typescript/blob/openapi-typescript%407.10.1/packages/openapi-typescript/package.json).
- Los tipos no validan JSON en ejecución: el cliente comprueba la estructura esencial y proyecta exclusivamente los campos públicos. Las escrituras reconstruyen explícitamente los DTO aprobados, aunque el objeto de entrada contenga propiedades adicionales.
- CSRF se obtiene por cada mutación y permanece en variables de la petición. No se reintentan escrituras automáticamente. La contraseña inicial se elimina del input al enviar, nunca se guarda en estado React, y no reaparece tras éxito/error. No se registran cuerpos, credenciales ni tokens.
- Los controles visibles orientan según el rol de sesión; las comprobaciones reales siguen en los guards del backend. No se implementan reglas de último administrador en el frontend.
- El exportador inicia Nest con `app.init()`, genera el documento y cierra la aplicación; no llama a `listen`, no envía solicitudes ni invoca persistencia. Se verificó sin `DATABASE_URL` ni `TEST_DATABASE_URL`. El runner de tipos elimina únicamente su directorio temporal propio.
- Los 793 renglones de `schema.d.ts` son código generado necesario para el contrato. ESLint excluye solo este archivo sin lógica ejecutable, con comentario justificativo. No se añadieron exclusiones de cobertura ni se rebajaron umbrales.
- `.github/workflows/ci.yml` ejecuta `pnpm api:types:check` tras generar Prisma Client y antes de typecheck. Conserva permisos `contents: read`, acciones fijadas, timeouts, instalación congelada y eventos existentes; no añade secretos ni servicios.

### Fallos intermedios declarados

- Al añadir la consulta de sesión, un mock reutilizaba una única `Response` para varias peticiones y consumía dos veces su body. Se corrigió el fixture para devolver respuestas nuevas y discriminar `/api/auth/session`; no se atribuye RED de producto a ese fallo.
- El primer E2E completo pasó 10/11: el selector de salud `getByRole('status')` era ambiguo al aparecer también carga de usuarios. Se acotó al estado de salud; siguientes ejecuciones 11/11 y cierre final 12/12.
- El primer `api:types:check` falló (1) porque Prettier resolvía distinta configuración en el directorio temporal. Se fijó explícitamente `.prettierrc.json`; el contrato coincidió después. La prueba posterior de fixture obsoleto es un control negativo del verificador, no TDD funcional.
- Typecheck detectó `exact` incompatible con `ByRoleOptions` (2) y ESLint detectó inicialización de la barrera de test (1). Se corrigió el test sin supresiones ni relajación de reglas; checks finales 0.
- El primer parseo YAML puntual falló por resolver `yaml` desde un enlace de pnpm (1). Se resolvió la ruta real de Vite y su dependencia existente; parseo posterior 0. `actionlint` no está instalado; no se instaló ni se afirma validación completa del esquema de GitHub Actions.

## Aislamiento, accesibilidad y revisión manual

El lanzador local usa `dotenv.parse` para extraer únicamente `TEST_DATABASE_URL` del archivo ignorado; no lo vuelca ni hace `source`. El proceso hijo recibe una allowlist con `PATH`, `HOME`, `TEST_DATABASE_URL`, sin `DATABASE_URL`. El runner valida loopback:5433 y `nextriva_test`, crea una base aleatoria `nextriva_test_i02_1_<32 hex>`, aplica migraciones y elimina exclusivamente esa base. No usa ni migra `nextriva_dev`, no elimina volúmenes ni ejecuta `migrate reset`.

Vitest comprueba etiquetas, `aria-invalid`, asociaciones `aria-describedby`, foco del primer error, confirmaciones y foco tras recarga controlada. Playwright recorre con Tab/Enter nombre, apellidos, email, contraseña, rol y botones; cancela, conserva cambios y descarta explícitamente sin crear una fila. También comprueba foco tras operaciones y ausencia de overflow a 375 px. Estas pruebas no equivalen a revisión manual con lector de pantalla ni a certificación WCAG.

Para repetir pruebas con una URL de test explícita ya configurada y válida, sin heredar URL de desarrollo:

```sh
unset DATABASE_URL
mise exec -- pnpm --filter @nextriva/web test
mise exec -- pnpm --filter @nextriva/api test:e2e
mise exec -- pnpm api:types:check
```

`TEST_DATABASE_URL` es obligatoria para E2E/integración y debe proporcionarla el operador de forma local sin imprimirla. El runner falla cerrado si falta o apunta a un destino no permitido. No se publican credenciales de ejemplo ni valores predeterminados.

Para validación humana, con API/web y una sesión ADMIN existente: comprobar listado; abrir alta; enviar vacío y revisar foco/errores; escribir datos sintéticos y cancelar, rechazar el descarte y comprobar valores; confirmar descarte; crear/editar y comprobar foco al terminar; activar/desactivar mediante confirmación. Repetir teclado y lector de pantalla en escritorio/móvil. Sin sesión, aparece el aviso correspondiente; este incremento no aporta un formulario de login.

La prueba de solicitud pendiente usa una promesa controlada, no sleeps.
