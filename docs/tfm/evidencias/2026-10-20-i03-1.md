# Evidencia TFM — I03.1 Backend de promociones

**Estado:** implementado; validación humana pendiente.

**Issue:** #37, `status:approved`.

**Alcance:** persistencia y API de promociones/fases; sin interfaz web.

## Decisiones y alcance aprobado

- Se añadieron únicamente `promotions` y `promotion_phases`; la promotora es única e implícita, sin tenant ni entidad de promotora.
- Campos de promoción: UUID, nombre (3–150), descripción opcional (máximo 1000), ubicación opcional (máximo 200), estado ACTIVE/ARCHIVED y fechas de creación/actualización.
- Fases: PLANNING, COMMERCIALIZATION, EXECUTIVE_PROJECT, CONSTRUCTION, PRE_HANDOVER, HANDOVER y AFTER_SALES. La API ordena la respuesta por este orden fijo y permite varias fases simultáneas.
- La sustitución de fases y cambios de la promoción son atómicos. Una promoción ACTIVE necesita al menos una fase. Archivar conserva las filas de fases; no hay operación de borrado de negocio ni cascada destructiva.
- Todas las rutas de promociones requieren sesión, CSRF para mutaciones y rol ADMIN verificado en servidor. MANAGER y COLLABORATOR no reciben acceso general en I03.1.
- Rutas implementadas: `GET/POST /api/promotions`, `GET/PATCH /api/promotions/:id` y `PATCH /api/promotions/:id/status`.
- Se generó el contrato cliente OpenAPI; no se añadió UI.

## TDD y pruebas

- **RED funcional observado:** antes de registrar la funcionalidad, las pruebas HTTP de I03.1 recibían 404 para las rutas y las pruebas PostgreSQL fallaban porque no existían las tablas/tipos de promociones. Para la regla de reactivación, se inyectó en PostgreSQL temporal una eliminación sintética de fases; el endpoint devolvió 503 frente al 400 esperado para la restricción de fase mínima.
- **GREEN observado:** la validación de fases vacías pasó al añadirse la regla. Para el error de commit, el mapeo recursivo de `sqlState`/`cause` corrigió la respuesta a 400; se comprobó rollback y conservación del estado archivado/fases. También pasaron edición completa, conflicto de unicidad y edición de ID inexistente.
- **Refactor/reverificación:** el traductor de error evita ciclos al buscar causas anidadas y no expone el detalle SQL en HTTP. Se repitieron suites de validación, persistencia y contrato. También se reparó una expectativa OpenAPI de autenticación que no incluía las rutas nuevas y un estrechamiento de tipo en la prueba OpenAPI.
- No se capturó un RED E2E separado antes de implementar el flujo de promociones. El E2E final sí crea y consulta una promoción contra la API real y comprueba persistencia PostgreSQL.
- La integración usa el runner existente y una base PostgreSQL temporal aislada. No se usó SQLite ni mocks como sustituto de PostgreSQL.

## Migración y persistencia

La migración versionada `apps/api/prisma/migrations/20261020120000_promotions/migration.sql` crea enums y tablas con FK `RESTRICT`, clave compuesta para las fases y restricción diferida para exigir fases en promociones activas. Fue aplicada desde cero por el runner sobre PostgreSQL temporal. La prueba directa observó `23503` para FK inválida, `23505` para fase duplicada, `23514` para promoción activa sin fase y `23001` al intentar borrar físicamente una promoción referenciada.

## Validación manual

1. Ejecutar la integración con el comando de PostgreSQL temporal de la tabla; el runner crea una base aislada y aplica migraciones desde cero.
2. Usar la cuenta ADMIN sintética que prepara el runner y autenticar vía `POST /api/auth/login`; obtener el token CSRF desde `GET /api/auth/csrf`.
3. Enviar `POST /api/promotions` con `{ "name": "Residencial Sintético", "description": "Prueba local", "location": "Madrid", "phases": ["AFTER_SALES", "PLANNING"] }`, incluyendo cookie de sesión, `Origin` y `X-CSRF-Token`. Esperar HTTP 201 y fases devueltas como `["PLANNING", "AFTER_SALES"]`.
4. Consultar `GET /api/promotions` y `GET /api/promotions/{id}`; confirmar que los datos persisten.
5. Autenticarse con una cuenta MANAGER sintética y repetir el GET. Esperar HTTP 403 y comprobar que el recuento de promociones no varía.
6. Cambiar estado mediante `PATCH /api/promotions/{id}/status` a ARCHIVED y después ACTIVE; consultar detalle y comprobar que se conservan exactamente las mismas fases.

Las credenciales y los valores locales se obtienen del entorno sintético de test; no se copian a documentación ni logs.
