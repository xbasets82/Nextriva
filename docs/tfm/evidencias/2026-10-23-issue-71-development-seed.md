# Herramienta — Datos ficticios para desarrollo local

Fecha: 23/10/2026. Issue #71, aprobado. Rama local `codex/chore-dev-seed`.

## Alcance implementado

El comando `db:seed:dev` genera datos sintéticos en `nextriva_dev`: 12 usuarios, 5 promociones, participantes, 60 incidencias por defecto, comentarios y actividades. La cantidad de incidencias se puede configurar entre 0 y 500. Los identificadores y la selección de datos son deterministas. La contraseña común `123456` se guarda con el `PasswordHasher` Argon2id existente y solo se aplica a las cuentas identificadas como seed; una ejecución repetida que ya verifica esa contraseña conserva el hash. Las cuentas manuales no se actualizan.

Solo se representan estados alcanzables con los flujos integrados: `OPEN`, `IN_PROGRESS` y `PENDING_VALIDATION`. No se inventaron actividades de aprobación o cierre de I07.3 ni se modificaron esquema y migraciones. El seed no se ejecuta automáticamente. El comando separado `db:seed:dev:clean` exige una confirmación exacta en terminal interactiva y rechaza referencias ajenas para preservar datos manuales. Ambas operaciones usan una transacción PostgreSQL; la preflight verifica identidades reservadas y rechaza colisiones antes de escribir.

La CLI rechaza CI y entornos de test/producción, así como destinos distintos de `nextriva_dev` en `127.0.0.1` o `localhost`, puerto `5432`. Solo lee `DATABASE_URL` del entorno o del archivo local ignorado `.env.local`; exige propiedad del usuario y permisos `0600` para el archivo. Comprueba también `current_database()` antes de la operación y oculta detalles de conexión en errores.

### Revisión posterior de propiedad y responsabilidades

Una revisión detectó dos defectos: una vinculación retirada y recreada con la misma clave podía confundirse con la del seed, y una nueva ejecución podía desactivar o degradar una cuenta seed responsable de una incidencia manual. Se añadieron primero tres casos de integración en la base PostgreSQL temporal: vinculación recreada con `joinedAt` distinto, desactivación y degradación. El comando seguro `env -u DATABASE_URL -u TEST_DATABASE_URL mise exec -- pnpm --filter @nextriva/api test:integration` produjo el RED esperado: 3 casos nuevos fallidos por promesas resueltas cuando se esperaba rechazo, 184 anteriores superados, 1 omitido; código 1. Una repetición con salida filtrada confirmó las tres causas, también con código 1.

El GREEN reutiliza `lockUserAdministration`, `assertResponsibilityReleased` y `assertIndependentValidatorRemains`. La limpieza compara también `joinedAt`, bloquea las promociones antes de comprobar y borrar, y elimina solo las claves y fechas exactas verificadas; así se coordina con la mutación normal de participantes. La misma suite pasó 187 pruebas, 1 omitida, código 0. El refactor extrajo la comprobación de cambios de usuario a una función privada para cumplir el límite de complejidad sin suprimir ESLint. Tras el refactor, la suite volvió a pasar 187 pruebas, 1 omitida, código 0. Las denegaciones se comprobaron con snapshots completos antes y después; no hubo mutaciones parciales. No se ejecutó el seed sobre `nextriva_dev`.

No se cambió el runner ni el comportamiento de E2E para evitar el fallo de puerto.
